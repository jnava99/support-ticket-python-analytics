# Support Ticket Python Analytics & SLA Monitor

A Python companion to [support-ticket-sql-analysis](https://github.com/jnava99/support-ticket-sql-analysis) — same underlying support-ticket dataset, analyzed with pandas instead of raw SQL, plus a small script that simulates the SLA-breach alerting logic behind tools like PagerDuty or Opsgenie.

## Why this project

The SQL project answers "what happened" with queries. This one shows the same kind of thinking in Python: loading and transforming data with pandas, generating charts, and — closer to my incident-management background — a simple monitor that flags tickets at risk of or already breaching their SLA.

## Structure

```
.
├── data/                # tickets.csv, agents.csv, customers.csv (same dataset as the SQL project)
├── analysis.py          # pandas analysis + chart generation
├── sla_monitor.py        # SLA breach/at-risk alert feed
├── charts/               # PNG charts generated by analysis.py
└── requirements.txt
```

## Setup

```bash
pip install -r requirements.txt
```

## Running it

**Analysis + charts:**
```bash
python analysis.py
```
Prints resolution-time, SLA-compliance, agent-workload, category, and top-customer summaries to the console, and saves three charts to `charts/`:
- `sla_compliance_by_priority.png`
- `tickets_by_category.png`
- `monthly_trend.png`

**SLA monitor:**
```bash
python sla_monitor.py
```
Scans currently open tickets and prints an alert feed, sorted by urgency:
- 🔴 **BREACHED** — already past its SLA target
- 🟡 **AT RISK** — within 2 hours of breaching
- 🟢 **OK** — comfortably within SLA (not shown in the alert feed)

Since this runs against a static historical dataset rather than a live system, the script treats the dataset's latest timestamp as "now" (see `SIMULATED_NOW` in `sla_monitor.py`) — in a real system you'd swap that for `datetime.now()`.

## Notes

- Uses the exact same synthetic dataset as the SQL project (same random seed), so results match across both — intentional, to show the same analysis approached two different ways.
- `sla_monitor.py` is deliberately simple (no real notifications sent) — it's meant to illustrate the triage logic, not replace an actual alerting platform.
